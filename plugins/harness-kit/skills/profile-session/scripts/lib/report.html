How to read this report

Cost units. input x w1 + cache read x w2 + cache write x w3 + output x w4 with the weights 1, 0.1, 1.25 and 5 unless the settings change them, summed over every model call of the main thread and its subagents. The weights are relative prices, not money; the token counts and weights of each session are stored in its record, so a value can be recomputed from it.

Subagent share. The part of the cost units spent by subagents. It is not in the per-call figures, which are main-thread only.

Units per main-thread call. Main-thread cost units divided by main-thread calls: the cost of an average call. A call re-reads the whole context, and the context grows during a session, so this figure grows with the length of the session: a 500-call session costs more per call than a 50-call one even under the same instructions. Compare sessions of different length by first 40 (70) calls, per call, the same average over only the first 40 (70) main-thread calls (empty for a shorter session), and by the length bands of the medians. The column sorts by the whole-session figure.

Duration, active / wall. Wall is the time from the first human turn to the last assistant line or tool result of the profiled period. Active is wall minus the time spent waiting for the user: from the end of each agent reply to the next human message, and from an AskUserQuestion or ExitPlanMode call to its answer. A permission prompt cannot be told apart from a long-running tool in the transcript, so its wait counts as active. The column sorts by active time.

Calls, human turns, start / max ctx. Main thread only. A human turn is a message from a person; background-task notifications, compaction summaries and local command output are not. A context is input + cache read + cache write of one call; start ctx is that of the first call, so it shows the size of the system prompt, instructions and tools loaded before any work, and max ctx is the largest of the session.

Cache hit. Cache-read tokens over cache-read plus cache-write tokens, main thread and subagents: how much of the context came from the cache rather than being written to it again.

Idle rebuilds and compactions (session breakdown). An idle rebuild is a call after a pause longer than the lifetime of the cache the session writes (one hour or five minutes, read from the transcript) that wrote over 30k tokens to the cache again. A compaction is a call whose context fell below 60 % of the previous one.

Weekly % used and units per 1 %. Recorded only when the session called get_usage (the Claude desktop app's plan-usage tool) at least twice: the first result in the transcript is the start reading, the last one the end. Only the cost between the two readings is related to the used percent, since the start reading already contains what the session spent before it. Both readings are whole numbers, so the percent really used is up to one point more or less than the difference; the session breakdown gives the range of units per 1 % this allows. Other use of the account in the same period (other sessions, chat) counts too, and the limit formula is not public and may weight models differently. Treat it as a trend indicator; 100 x units per 1 % is only an estimate of the weekly allowance in units for the same plan and model.

Account. org- and the first four hex digits of the SHA-256 of the organization id in the transcript; the id itself is never stored. Empty for transcripts of Claude Code versions that do not record it.

Changed vs previous session (the i icon next to the work item, which also shows the note of the session; the M icon next to it shows the marker of the session, a label such as the change of rules the session was the first to run under). A different model, Claude Code version, cache lifetime or set of cost weights than the previous session in time order (over all records, not only the filtered ones), one per line: a change of cost there may come from that, not from the instructions; sessions costed with different weights are not comparable in cost units. A cache change is flagged only when both sessions have a value. The account is not flagged: it is shown in its own column and does not change the token figures; the medians have a row per account.

Medians. One row per lane (Bug or Feature), session length band and account (each account has its own plan and limit; records without an account form "(unknown)"), and one over all sessions, for the sessions that pass the filters. The columns are those of the trend table, each the median of that column over the group; the duration cell holds the median active and the median wall time, which may come from different sessions. Compare groups of different length by the first-40-calls figure, which does not depend on session length. Units per 1 % in a lane, length or all-sessions row marked "mixed accounts" comes from sessions of more than one account; only the account rows compare like with like.

Accuracy. Token totals and context sizes are exact (API usage). The split by activity is inferred from the tools each call used. The commit is read when the session is profiled, not when it ran, and is empty for a record amended into that commit. A workflow that profiles its session before shipping leaves the last actions (push, pull request, time report) out of the profile. With only a few sessions the trend is indicative, not statistically reliable; a benchmark that runs fixed test sessions is the repeatable reference.
